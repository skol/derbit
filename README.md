# Тестовое задание на позицию junior backend разработчика

## Задание:

1. Написать клиент для криптобиржи [Deribit](https://docs.deribit.com/). Клиент должен каждую минуту забирать с биржи
   текущую цену `btc_usd` и `eth_usd` (index price валюты) после чего сохранять в базу данных тикер валюты, текущую цену и
   время в UNIX timestamp.
2. Написать внешнее API для обработки сохраненных данных на FastAPI. Обязательные требования: 
   1. API должно включать в себя следующие методы:
      - Получение всех сохраненных данных по указанной валюте
      - Получение последней цены валюты
      - Получение цены валюты с фильтром по дате
      
      Все методы должны быть GET и у каждого метода должен быть обязательный query - параметр `ticker`.
   
   2. В качестве БД использовать PostgreSQL.
   3. Код выложить на gitlab с подробным readme и документацией по разворачиванию. В readme добавить секцию Design decisions.
   4. Для периодического получения цен использовать Celery.
3. Необязательные требования:
   1. Написать unit тесты для основных методов
   2. Развернуть приложение в двух контейнерах для приложения и базы данных.
   3. Применить aiohttp при написании клиента.

## Структура проекта

### Настройки docker

Файл `docker-compose.yml` содержит объявление сервисов проекта.
Файл `Docker` описывает сборку образа целевого FastAPI приложения.
Файл `.env` содержит текущие секреты проекта. Создается на основе `.env.example`, подставляются свои значения.

### Приложение

Приложение состоит из 2 частей: 
- задачи `fetch_prices_task` для celery, собирающей данные с биржи deribit (файл `app/hard/fetch.py`)
- fastapi приложения, предоставляющего api к собранным данным (файл `app/hard/main.py`)

### Миграции

Папка `alembic` и файл `alembic.ini` предназначены для управления схемой данных приложения. 

### Тесты

В папке `tests` содержатся тесты по проекту. Запускаем с помощью `pytest`.

## Запуск проекта

- клонируем репозиторий с помощью `git clone https://github.com/skol/derbit.git`
- заходим в папку `derbit`
- если отсутствуют, создаем папки `data/postgres` и `data/redis`
- вызываем `docker-compose up -d --build` (ключ `--build` важен только для сборки образа, для запуска после останова его
  использовать не обязательно)
- переходим на `http://127.0.0.1:9999/docs`

## Design decisions:

1. Первая развилка, которая встретилась при реализации - это выбор, что делать при проблемах с доступом к бирже (кейсы):
   - оборвался текущий запрос одного курса, остальные в этой сессии, до и после сбойного, прошли
   - оборвались все запросы одного курса, остальные прошли
   - оборвались все запросы, начиная с текущего момента и до конца сессии
   - оборвались все запросы во всех сессиях с текущего момента

   политика поведения больше бизнесовая, и вопрос должен уйти заказчику
2. Вторая, сохранение метки времени: 
   - хранить можно локальное время сервера, когда он начал задачу в целом
   - можно хранить время, когда он спросил именно этот текущий курс у биржи
   - можно хранить время, когда сервер биржи ответил на запрос (поле usOut в ответе)
3. Celery использовал исключительно исходя из требований задачи. В данном случае, тестового задания и крайне небольшой
   нагрузки, можно было обойтись `asynccontextmanager`, асинхронной функцией, и запуском рядом с api.
4. Пул соединений с БД глобален по своей природе, и в этом моменте выбор был вполне осознанным.
